# ClickHouse数据库表设计方案对比分析

## 🎯 方案对比

### 方案A：统一表 + symbol区分（✅ 推荐 - 当前采用）

```
forex_data
├── ohlcv_m1   (所有货币对的M1数据)
├── ohlcv_d1   (所有货币对的D1数据)
├── ohlcv_m5   (所有货币对的M5数据)
├── ohlcv_m15  (所有货币对的M15数据)
├── ohlcv_m30  (所有货币对的M30数据)
└── ohlcv_h1   (所有货币对的H1数据)

总计: 6个表
```

**数据示例**:
```sql
SELECT * FROM forex_data.ohlcv_m1 WHERE symbol IN ('EURUSD', 'GBPUSD', 'USDJPY')
```

### 方案B：按货币对分表（❌ 不推荐）

```
forex_data
├── eurusd_m1, eurusd_d1, eurusd_m5, eurusd_m15, eurusd_m30, eurusd_h1
├── gbpusd_m1, gbpusd_d1, gbpusd_m5, gbpusd_m15, gbpusd_m30, gbpusd_h1
├── usdjpy_m1, usdjpy_d1, usdjpy_m5, usdjpy_m15, usdjpy_m30, usdjpy_h1
├── usdcad_m1, usdcad_d1, usdcad_m5, usdcad_m15, usdcad_m30, usdcad_h1
├── usdchf_m1, usdchf_d1, usdchf_m5, usdchf_m15, usdchf_m30, usdchf_h1
└── audusd_m1, audusd_d1, audusd_m5, audusd_m15, audusd_m30, audusd_h1

总计: 36个表（6货币对 × 6时间框架）
```

## 📊 详细对比表

| 维度 | 方案A：统一表 | 方案B：分表 |
|------|--------------|------------|
| **表数量** | 6个 | 36个（6货币对）<br>如果添加股票，会更多 |
| **扩展性** | ✅ 极好：添加新品种只需插数据 | ❌ 差：每个新品种需建6个表 |
| **查询灵活性** | ✅ 优秀：单SQL查多品种 | ❌ 差：需要UNION多个表 |
| **管理复杂度** | ✅ 低：统一配置 | ❌ 高：每个表单独管理 |
| **物化视图** | ✅ 简单：4个物化视图 | ❌ 复杂：24个物化视图 |
| **存储效率** | ✅ 优秀：symbol字段压缩率高 | ⚠️ 一般：表元数据开销大 |
| **性能** | ✅ 优秀：分区+索引优化 | ⚠️ 一般：查询时需要union |
| **备份恢复** | ✅ 简单：6个表 | ❌ 复杂：36+个表 |

## 🔄 M1和D1分离的必要性

### 数据特征对比

| 特征 | M1数据 | D1数据 |
|------|--------|--------|
| **数据量** | 海量（单货币对年百万级） | 中等（单货币对年365条） |
| **查询频率** | 高频（策略回测） | 中频（长期分析） |
| **时间跨度** | 短期（天/周/月） | 长期（月/年） |
| **分区策略** | 按月（`toYYYYMM`） | 按年（`toYear`） |
| **索引粒度** | 8192（默认） | 可以更小 |
| **压缩策略** | LZ4（速度优先） | ZSTD（压缩率优先） |
| **缓存策略** | 热数据缓存（最近几天） | 全量缓存（数据量小） |

### 性能影响示例

#### 如果M1和D1合并到一张表：

```sql
-- 查询D1数据时需要过滤海量M1数据
SELECT * FROM ohlcv WHERE symbol='EURUSD' AND timeframe='D1' AND date >= '2020-01-01'
-- 问题：需要扫描所有M1数据的索引
```

#### 分开后：

```sql
-- 直接查询D1表，无需过滤
SELECT * FROM ohlcv_d1 WHERE symbol='EURUSD' AND date >= '2020-01-01'
-- 优势：只扫描D1表，性能提升10倍以上
```

## 🎯 最佳实践建议

### ✅ 推荐的设计（当前方案）

```sql
-- 表结构
ohlcv_m1 (symbol, timestamp, open, high, low, close, volume)
ohlcv_d1 (symbol, date, open, high, low, close, volume)

-- 查询示例
-- 1. 单货币对查询
SELECT * FROM ohlcv_m1 WHERE symbol = 'EURUSD' AND timestamp >= '2025-01-01'

-- 2. 多货币对对比
SELECT symbol, avg(close) as avg_price
FROM ohlcv_m1
WHERE symbol IN ('EURUSD', 'GBPUSD', 'USDJPY')
  AND timestamp >= '2025-01-01'
GROUP BY symbol

-- 3. 跨品种相关性分析
SELECT 
    a.timestamp,
    a.close as eurusd_price,
    b.close as gbpusd_price
FROM ohlcv_m1 a
JOIN ohlcv_m1 b ON a.timestamp = b.timestamp
WHERE a.symbol = 'EURUSD' AND b.symbol = 'GBPUSD'
  AND a.timestamp >= '2025-01-01'
```

### 🔧 优化建议

1. **索引优化**
   ```sql
   -- 主键已经是 (symbol, timestamp)，支持最常见查询
   -- 如需按时间范围查询所有品种，当前索引已最优
   ```

2. **分区策略**
   ```sql
   -- M1按月分区，便于删除旧数据
   ALTER TABLE ohlcv_m1 DROP PARTITION '202001'
   
   -- D1按年分区，管理简单
   ALTER TABLE ohlcv_d1 DROP PARTITION '2020'
   ```

3. **添加新品种**
   ```sql
   -- 无需建表，直接插入数据
   INSERT INTO ohlcv_m1 VALUES ('AAPL', '2025-01-01 09:30:00', 150.0, ...)
   INSERT INTO ohlcv_d1 VALUES ('AAPL', '2025-01-01', 150.0, ...)
   ```

4. **查询优化**
   ```sql
   -- 使用 symbol IN (...) 而非多次查询
   -- ClickHouse 会并行处理每个 symbol
   SELECT * FROM ohlcv_m1 
   WHERE symbol IN ('EURUSD', 'GBPUSD', 'USDJPY', 'AAPL', 'GOOGL')
     AND timestamp >= '2025-01-01'
   ```

## 🚀 未来扩展场景

### 场景1：添加股票数据

```sql

INSERT INTO ohlcv_m1 SELECT 'AAPL', timestamp, open, high, low, close, volume FROM stock_csv
INSERT INTO ohlcv_d1 SELECT 'AAPL', date, open, high, low, close, volume FROM stock_csv

-- 查询时可以混合外汇和股票
SELECT symbol, avg(close) 
FROM ohlcv_d1
```

## 📝 结论

### ✅ 当前设计（方案A）是最佳选择

**原因：**

1. ✅ **统一表** - 所有货币对/股票共用6个表
2. ✅ **M1和D1分离** - 数据特征不同，性能优化不同
3. ✅ **扩展性强** - 添加新品种无需建表
4. ✅ **管理简单** - 6个表 vs 36+个表
5. ✅ **查询灵活** - 单SQL处理多品种
6. ✅ **性能优秀** - ClickHouse列式存储天然适合

### 🎯 设计原则

- **表的划分依据**：数据特征（时间粒度、数据量）
- **品种的划分依据**：字段值（symbol字段）
- **不要为每个品种建表**：这是传统关系型数据库的思维

### 💡 一句话总结

> **在ClickHouse中，用字段区分品种，用表区分数据特征**
